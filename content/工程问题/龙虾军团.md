# 多agent协作的背景知识
从哲学和社会学角度看，完成一项事业（即“干好一个事”）所需的最少角色，可以提炼为**两个核心角色**：**决策者（引领者）** 与 **执行者（行动者）**。这两个角色构成了人类社会最基本的协作单元，无论是黑格尔的“主奴辩证法”中主人与奴隶的相互承认，还是管理学中“领导-执行”的二分，都体现了这种二元结构。决策者负责设定目标、规划路径；执行者负责将意志转化为现实。二者相互依存，缺一不可。

若进一步考虑协作中的协调与反馈，社会学视角下的功能分化可能引入第三个角色——**监督者/评估者**，用以平衡权力、纠正偏差，例如孟德斯鸠的三权分立或帕森斯的AGIL模型中的“维持模式”功能。但在最简意义上，两个角色已能启动并完成一件事，第三个角色是对协作质量的保障而非存在的前提。

# 详细内容
你贴的这个配置确实体现了一个 **典型的串行流程 (serial workflow)**，让我帮你分析清楚。

---

## 1️⃣ 流程结构分析

从你给的 `allowAgents` 链来看：

```
main → decider → executor → supervisor → decider
```

- **main**：入口，接收任务
    
- **decider**：拆解任务并分配
    
- **executor**：执行具体操作
    
- **supervisor**：检查执行结果是否合理
    
- **decider**（回到决策者）形成闭环
    

特点：

- **严格串行**：每个 agent 都要等待上一个 agent 完成任务后才能开始下一步。
    
- **闭环回流**：supervisor 会把结果或问题回传给 decider 进行再处理。
    

---

## 2️⃣ 优缺点

### 优点

1. **逻辑清晰**：每个 agent 责任单一，流程线性，便于追踪错误。
    
2. **可控性高**：任务按顺序执行，容易保证状态一致性。
    
3. **调试方便**：中间结果容易观察，问题出现时定位具体 agent。
    

### 缺点

1. **瓶颈明显**：整个系统速度受限于最慢的 agent（典型串行延迟）。
    
2. **容错差**：一旦中间某个 agent 异常，整个流程可能中断。
    
3. **资源利用低**：执行者空闲时，其他 agent 也在等待，无法并行处理多任务。
    
4. **闭环回流可能造成死循环**：supervisor → decider → executor，如果任务无法通过检查，可能一直循环。
    

---

## 3️⃣ 串式调用中断的原因分析

你提到“实际运行中经常中断”，结合你的串行结构，有几个可能原因：

1. **单点失败**
    
    - 任何一个 agent 出错，链条就断了。
        
    - 例如 executor 超时、模型报错或超出 token 限制。
        
2. **资源竞争 / 内存不足**
    
    - 多 agent 串行运行，占用大量内存/CPU，如果模型过大（vllm），可能导致中途失败。
        
3. **循环闭环问题**
    
    - supervisor 回传给 decider，如果 decider 没有终止条件，可能触发无限调用，或者因为任务状态不明确导致拒绝执行。
        
4. **网络/IO问题**（如果调用了外部工具）
    
    - 串行流程中没有并行冗余，一旦外部依赖慢或失败，就会阻塞整个链。
        

---

## 4️⃣ 改进思路

1. **引入并行 / 异步处理**
    
    - executor 可以支持多线程或批量任务处理，减少串行等待。
        
    - 对非关键任务，可以 decider 下发多个 executor 同时执行。
        
2. **中断保护 / 超时机制**
    
    - 每个 agent 配置 `timeout` 和错误重试。
        
    - 超时或失败时返回默认状态，而不是完全中断。
        
3. **任务状态追踪**
    
    - main 维护任务队列和状态，避免闭环重复执行。
        
4. **拆分任务粒度**
    
    - 避免一次任务太大，导致 executor 或 supervisor 处理失败。
        

---

总结：

- 你现在是典型 **串行 + 闭环** 模式，适合任务顺序强依赖、调试优先的场景。
    
- 问题主要是 **中途失败导致整个链条断掉**，可以通过 **并行化、超时保护、任务分块** 来改善。

下面给你一个 **更适合 OpenClaw + 飞书群 + subagent 机制的结构设计**。目标是解决你现在遇到的三个问题：

- 串行链路 **容易中断**
    
- **subagent 闭环调用不稳定**
    
- **飞书群响应容易超时**
    

核心思想是：

> **入口统一 + 决策拆解 + 执行并行 + 监督回收 + 避免 agent 循环调用**

也就是 **树状结构，而不是链式结构**。

# 一、推荐的 Agent 结构

把你现在的：

```
main → decider → executor → supervisor → decider
```

改成：

```
                main
                 │
              decider
        ┌────────┼────────┐
     executor1  executor2  executor3
        └────────┬────────┘
             supervisor
```

核心变化：

**不再允许 agent 互相循环调用。**

所有 agent 只向 **下游调用**。

# 三、任务运行流程

飞书群消息流程：

```
飞书群
  ↓
main
  ↓
decider
  ↓
executor (执行任务)
  ↓
supervisor (审核结果)
  ↓
decider (汇总)
  ↓
main
  ↓
飞书群回复
```

这样：

- agent **调用深度最多 3 层**
    
- 不会出现 **递归调用**
    
- 不会出现 **subagent 死循环**

# 四、为什么你现在会经常中断

你当前结构：

```
main
 ↓
decider
 ↓
executor
 ↓
supervisor
 ↓
decider
```

问题：

### 1 agent recursion

OpenClaw 对这种 **循环调用非常不稳定**

```
decider → executor → supervisor → decider
```

很容易触发：

- context overflow
    
- agent stack error
    
- tool call recursion
    

---

### 2 context 不断累积

每一轮：

```
decider
executor
supervisor
decider
```

都会增加上下文。

几轮之后：

```
prompt > context window
```

就炸了。

你之前其实已经遇到：

```
Context overflow
```

---

### 3 飞书响应时间

飞书 webhook：

通常 **10秒以内必须返回**。

如果你的链是：

```
main → decider → executor → supervisor → decider → executor
```

很容易超过。

# 五、最佳实践（OpenClaw 多 Agent）

推荐模式：

### ⭐ 1 入口 agent

```
main
```

职责：

- 接收消息
    
- 分配任务
    
- 汇报结果
    

不要做复杂工作。

---

### ⭐ 2 orchestration agent

```
decider
```

职责：

- 任务拆解
    
- 调用 executor
    
- 汇总结果
    

这是 **系统大脑**。

---

### ⭐ 3 worker agent

```
executor
```

职责：

- 实际执行
    
- 调工具
    
- 写文件
    
- 搜索
    

---

### ⭐ 4 reviewer agent

```
supervisor
```

职责：

- 校验
    
- 评分
    
- 提出改进
    

但 **不要再触发任务**。
