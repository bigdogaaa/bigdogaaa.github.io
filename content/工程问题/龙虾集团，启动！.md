### 为什么要用多个Agent？先回到人类社会的最简协作模型

在构思“龙虾集团”这个多Agent系统时，我反复问自己一个问题：**完成任何一项事业，最少需要几种角色？**

这个问题看似技术，实则关乎底层逻辑。我们不妨先跳出代码，从哲学和社会学的源头找答案。

人类历史上最经典的协作二元结构，莫过于黑格尔在《精神现象学》中提出的**“主奴辩证法”** 。在这一对关系中，主人是纯粹的“决策者”，他制定目标、享受成果，但他依赖于奴隶的执行；奴隶是纯粹的“执行者”，通过劳动改造世界，却在实践中逐渐掌握了认识和改造世界的真知 。两者相互依存、相互斗争，又相互承认，构成了一个完整的行动闭环。虽然黑格尔讨论的是意识的演化，但这隐喻了一个朴素的事实：**意志必须通过行动才能变现，而行动必须依赖意志的指引。**

到了现代管理学，这种二元结构被进一步抽象为 **“领导”与“管理”** 的分离。领导者的核心是决策，负责定方向、绘愿景；管理者的核心是执行，负责定计划、控流程、拿结果 。正如现代企业制度所证明的，当决策权和执行权在分权基础上明确分离，组织的效率才能最大化 。一个既要做决策又要亲自执行所有细节的领导者，往往会陷入“微观管理”的陷阱，成为团队效率的瓶颈 。

因此，从意识哲学到组织行为学，我们都可以提炼出完成一项事业所需的**两个核心角色**：
1.  **决策者（引领者）**：负责设定目标、规划路径、评估风险。
2.  **执行者（行动者）**：负责调用工具、操作细节、将意志转化为现实。

这二者相互依存，缺一不可。没有执行者的决策者是空想家；没有决策者的执行者是盲目的工具。

### 从二元到三元：当系统需要纠偏与平衡

当然，这只是最简模型。如果你希望这个协作系统不仅仅是“能跑起来”，而是“跑得稳、跑得远”，那么往往需要引入第三个角色——**监督者/评估者**。

这在社会学和政治学中有着更深刻的印证。孟德斯鸠在《论法的精神》中提出的**“三权分立”**，本质上就是在决策（行政）和执行（司法/立法细化）之外，引入了独立的监督与制衡力量，以防止权力的滥用和系统的崩溃 。

社会学家帕森斯的结构功能主义则看得更透。他提出的**AGIL功能模型**指出，任何行动系统要想存续，必须满足四项基本功能 ：
- **适应（A）**：从环境中获取资源——对应**执行**。
- **目标达成（G）**：确定目标并调动资源实现它——对应**决策**。
- **整合（I）**：协调系统各部分，防止冲突——对应**监督与协调**。
- **潜在模式维持（L）**：确保系统的价值观和运行规则得以延续。

帕森斯的模型告诉我们，一个成熟的系统，除了“干活”的和“指挥”的，还需要一个角色来“维持秩序”和“纠正偏差”。这个第三方的存在，是对协作质量的保障，而非存在的前提。

### 回到多Agent系统：为什么单大模型搞不定？

理解了人类社会的协作模型，再来看大模型，问题就清晰了。

当前的大模型，无论是GPT-4还是其他，本质上是一个“坐在办公室里的全能天才”。它既想当决策者，又想当执行者。但实践中你会发现：
1.  **角色冲突**：当它需要同时处理战略规划和具体编码时，注意力资源会被稀释，导致“样样通，样样松”。
2.  **缺乏制衡**：单一大模型容易出现“自我强化”的幻觉，它制定了一个错误计划，然后执行了这个错误计划，整个过程缺乏一个独立的“监督者”来踩刹车 。
3.  **上下文过载**：把所有任务塞进一个大脑，会导致上下文窗口爆炸，Token消耗巨大，且效率低下。

**多Agent架构的最大优势，恰恰在于对社会协作模式的模拟。** 它通过角色的解耦，实现了“决策-执行-监督”的职能分离。

基于OpenClaw设计架构时，我们就借鉴了这种思想。我们不会试图造一个“全能神”，而是打造一个 **“龙虾集团”**——每个Agent各司其职：
- **决策层Agent**：负责理解用户意图，拆解任务，制定战略计划。
- **执行层Agent**：负责调用具体工具（如浏览器、代码解释器、API），完成具体动作。
- **监督层Agent（协调者）**：负责监控任务进度，评估中间结果，在决策和执行之间建立反馈闭环，甚至在决策失误时提出修正建议。

这种架构的最大红利在于**鲁棒性和可扩展性**。当某个执行Agent失败时，不影响决策层的稳定；当我们需要引入新能力时，只需添加一个新的“奴隶”Agent，而无需重构整个“主人”的意识 。

> 下一节，我们将详细拆解，在OpenClaw的实践中，如何设计这套“主奴”之间的通信协议与任务编排机制，让“龙虾集团”真正高效地运转起来。


## 如何设计这套主奴通讯机制

从哲学思辨落到技术实现，中间隔着一条叫“落地”的河。在让“龙虾集团”真正跑起来的路上，我踩了不少坑。这些坑有的来自对 OpenClaw 机制的理解偏差，有的来自多 Agent 协作天生的复杂性。所幸，每一次掉坑都是一次对架构的重新理解。

### 我的多 Agent 演进之路：从群聊混乱到分层架构

回顾我尝试多 Agent 的过程，大概经历了五个阶段，每一个阶段都在解决上一阶段的痛点：

1.  **多个群分别 @**  
    最早的想法很简单：给每个角色建一个飞书群，需要哪个角色就去哪个群 @ 对应的机器人。结果协作非常麻烦——一个问题可能要跨三四个群复制粘贴，上下文割裂得像碎纸机搅过一样。

2.  **一个群，需要时才 @**  
    于是我把所有机器人拉进同一个群，想用的时候 @ 对应的 bot。但很快发现，机器人之间不会自动接力——我必须手动 @ 下一个，不然流程就断了。这哪是智能体，分明是提线木偶。

3.  **多个 Agent 放入一个群，无需 @**  
    听说 OpenClaw 支持多 Agent 自动响应，我试了把多个 Agent 都 bind 到同一个群，不加 @ 前缀。结果可想而知：上下文混乱，角色经常串，明明问的是编程问题，执行者却抢着写文案。任务边界根本划分不清。

4.  **对 Agent 结构进行梳理，变为串行，只留一个主群，保留一个 Agent 用于和用户对接，编写 SOUL 文件，让 Agent 安排手下干活**  
    痛定思痛，我开始参考 OpenClaw 的 **subagent 机制**。配置了 `main` 作为对外的接口，它下面允许 spawn `decider`，`decider` 再调用 `executor` 和 `supervisor`。这就像公司里只有 CEO 对外，CEO 把任务拆给高管，高管再指挥具体干活的人。  
    但这个阶段还是串行的：`main` 把任务交给 `decider`，`decider` 必须等 `executor` 执行完才能继续，整个链条变长，效率低，而且偶尔会因为某个环节超时而中断。

5.  **优化为并行架构，去掉循环依赖**  
    后来我调整了结构：`main` 仍然负责对接用户，但收到任务后，直接 spawn 多个并行的 `decider`？不，更合理的是让 `decider` 本身成为任务分解中心，它可以同时启动多个 `executor` 并行执行子任务，`supervisor` 则独立监控所有执行过程，必要时介入。这样就变成了  
    `main → decider → (executor1, executor2, ...) + supervisor`  
    去掉了循环依赖（比如 executor 又去调 decider），任务吞吐量明显提升。

6.  **支持子 Agent、孙 Agent**  
    随着需求复杂，我发现 `executor` 本身也可能需要分工。比如一个编程任务，可能需要代码生成、代码检查、文档编写三个不同的 executor 配合。于是我在配置里允许 `executor` 也可以 spawn 自己的 subagent，形成两层甚至三层嵌套。OpenClaw 的 `subagents.maxSpawnDepth` 参数正好支持这种深度。

### 部署中最坑的一环：Bindings 配置

在演进过程中，我遇到过一个非常迷惑的现象：明明配置了四个 Agent，也分别绑定了不同的飞书 Bot，但不管在哪个群 @ 哪个 bot，回应的总是 `main`。

这个问题折腾了我一整天，最后发现是 **Bindings 机制** 理解不到位。这里值得花点篇幅彻底讲清楚。

#### 🔗 Bindings 是什么？为什么它是多 Agent 的核心？

简单来说，**`bindings` 就是一个路由表**，它告诉 OpenClaw：“当收到来自某个特定聊天窗口的消息时，应该由哪个 Agent 来负责处理”。

*   **核心原理**：你不需要为每个 Agent 部署一套独立的 OpenClaw 实例。只需一个 OpenClaw 实例，通过 `bindings` 配置，就能让不同的飞书群组（或私聊）对应不同身份和能力的 Agent。在 A 群里 @ 机器人，回复你的是“决策者”；在 B 群里 @ 机器人，回复你的则变成了“执行者”。

*   **为什么之前一直由 `main` 响应？**  
    关键在于 **fallback 机制**。如果消息来源的群组没有在 `bindings` 中找到精确匹配的规则，或者匹配规则本身有问题，OpenClaw 就会找不到该由谁来处理。当匹配失败时，OpenClaw 会将消息交给一个默认的 Agent 处理——在我的配置里，这个默认兜底的就是 `main`。这完美解释了为什么所有群的消息最终都由 `main` 回应。

#### ⚙️ Bindings 的标准配置格式（结合我的配置文件）

看一下我现在的 `bindings` 配置（取自 `openclaw.json`）：

```json
"bindings": [
  {
    "agentId": "main",
    "match": {
      "channel": "feishu",
      "accountId": "general-bot"
    }
  },
  {
    "agentId": "decider",
    "match": {
      "channel": "feishu",
      "accountId": "decider-bot"
    }
  },
  {
    "agentId": "executor",
    "match": {
      "channel": "feishu",
      "accountId": "executor-bot"
    }
  },
  {
    "agentId": "supervisor",
    "match": {
      "channel": "feishu",
      "accountId": "supervisor-bot"
    }
  }
]
```

这个配置看起来没问题，但实际上少了一个关键字段：**`peer`**。`peer` 用于指定具体的聊天窗口（群或私聊的 ID）。如果只写 `accountId`，OpenClaw 并不知道这个绑定是针对哪个群或哪个用户的——它会把所有发给这个飞书账号的消息都路由到这个 Agent，但如果这个账号同时被多个群使用，就会导致混乱。

正确的做法是：在 `match` 里加上 `peer`，明确指定这个 binding 适用于哪个群或哪个用户。例如：

```json
{
  "agentId": "decider",
  "match": {
    "channel": "feishu",
    "accountId": "decider-bot",
    "peer": {
      "kind": "group",
      "id": "oc_xxxxxx"   // 具体的群 ID
    }
  }
}
```

如果希望一个 bot 只在一个群里工作，就必须指定 `peer.id`。如果希望一个 bot 在所有群里都工作（不推荐），可以省略 `peer`，但这样可能会和其他 binding 冲突。更规范的做法是，为每个 Agent 创建独立的飞书应用（Bot），然后每个 binding 都指定明确的 `peer`。

#### 🧩 飞书账号配置（accounts）的坑

另一个容易踩的坑是飞书账号的配置格式。在我的配置中，`channels.feishu.accounts` 是一个对象，每个 key 对应一个 bot 的配置。这是符合 OpenClaw 要求的。但早期我曾错误地把 `accounts` 写成了数组，导致 OpenClaw 解析失败，所有 binding 都失效，全部 fallback 到 main。

#### 📡 飞书事件订阅方式

OpenClaw 与飞书集成推荐使用 **长连接（WebSocket）**，而不是 HTTP 回调。需要在飞书开发者后台的应用配置中，将“事件与回调”的订阅方式设置为“使用长连接接收事件”。这样不需要公网 IP，也不怕端口暴露。我的配置文件里没有显式设置，但 OpenClaw 默认会启用 WebSocket 模式。

#### ✅ 必要的飞书权限

确保每个飞书应用都开通了以下权限：
- `im:message`（基础消息能力）
- `im:message.p2p_msg:readonly`（读取私聊消息）
- `im:message.group_at_msg:readonly`（接收群聊@消息）
- `im:message:send_as_bot`（以机器人身份发送消息）

### 核心设计理念：四个 Agent 的分工与演进

经历了这些折腾，我逐渐形成了一套稳定的多 Agent 设计理念，也写进了配置文件里：

- **整个系统只有 4 个核心 Agent**：`main`（对外接口）、`decider`（决策者）、`executor`（执行者）、`supervisor`（监督者）。这呼应了第一部分提到的“决策-执行-监督”三元结构。
- **Decider 要设计好分化和演进方法**：目前它只能 spawn `executor` 和 `supervisor`，但随着任务复杂，它需要能识别任务类型，调用正确的专业 Agent（如 Research Agent、Code Agent、Writer Agent）。
- **不要调用不存在的 Agent**：Decider 必须知道自己手下有哪些兵，避免瞎指挥。
- **给 Agent 注入最小化知识**：每个 Agent 的 `workspace` 里的 `SOUL.md` 只描述它的职责和边界，不要塞太多无关信息。
- **专注特定领域，形成长期演化能力**：比如未来我可以让 Code Agent 专门积累代码库知识，Writer Agent 专门积累写作风格，这样它们的能力会越来越强，而不是什么都懂一点但什么都不精。

### 长期演化方向

目前我的结构是：
```
main(1) → decider(1) → executor(1) + supervisor(1)
```
这只是一个起点。未来的演化方向是：
```
main(1) → decider(1) → executor 分化为多个专精 Agent
                          ├─ research agent
                          ├─ code agent
                          ├─ analyst agent
                          └─ writer agent
                 + supervisor(1)
```
要实现这个分化，decider 需要具备任务分类能力，并且能根据任务类型动态调用正确的 executor。每个 executor 的 workspace 里只放该领域的最小知识，避免干扰。

### 小结

从多个群聊的混乱，到串行结构，再到并行分层，最后通过 bindings 精确路由，这个过程让我深刻体会到：多 Agent 不是简单地把多个模型实例丢进同一个群，而是需要精心设计角色、边界和通信机制。OpenClaw 的 subagent 和 bindings 机制提供了足够的灵活性，但理解其背后的原理（fallback、peer 匹配）是避免踩坑的关键。
