# Q: 为什么现在的大模型会工具调用？怎么实现的？关键过程是什么？
这是一个很好的问题，它触及了当前大模型应用中最核心、最实用的技术之一。

简单来说，**大模型的工具调用能力，本质上是给一个只会“纸上谈兵”的理论家装上了手和脚，让它能够真正地去“做事”和获取“一手信息”**。

下面我们来详细拆解：为什么需要它？它是怎么实现的？以及最关键的执行过程是怎样的。


### 一、为什么大模型需要工具调用？

纯粹的大模型（如早期的GPT系列）是一个**“文本生成器”**，它存在几个天然的短板：

1.  **知识是静态的**：它的知识截止于训练数据的那一刻，无法获取最新的信息（如今天的天气、实时股价）。
2.  **无法执行精确计算**：虽然能做一些简单数学，但对于复杂、高精度的计算（如微积分、解方程），它容易出错，更擅长的是“语言处理”而非“计算”。
3.  **与现实世界隔绝**：它无法主动采取行动，比如帮你发一封邮件、查询数据库、或者控制智能家居设备。
4.  **容易产生“幻觉”**：当它不知道答案时，为了生成通顺的文本，可能会“编造”一个听起来合理的答案，而不是诚实地告诉你它不知道。

**工具调用的出现，就是为了解决这些问题。** 它让大模型从一个**“思考者”**变成了**“行动者”**。

### 二、工具调用是怎么实现的？关键过程是什么？

实现工具调用的核心在于 **“意图识别”**和 **“结构化输出”**。整个流程可以分解为以下几个关键步骤：

#### 关键过程全景图

1.  **用户提问**：用户提出一个需要实时信息或执行动作的问题。
2.  **模型决策（意图识别）**：大模型分析用户的问题，判断自己是否需要使用工具。如果需要，它决定调用哪个工具，并按照工具的“说明书”（API描述）生成一个**结构化的调用指令**。
3.  **执行工具**：系统（而非模型本身）接收到这个指令，去调用真实的API，比如天气API、计算器或数据库。
4.  **获取结果**：工具执行后，将结果（如天气数据、计算结果）返回给系统。
5.  **模型整合回答**：大模型拿到工具返回的真实数据，结合用户最初的问题，生成一个最终的自然语言回答。
6.  **呈现给用户**：用户看到的是一个准确、实时的答案。

#### 详细拆解：关键步骤是如何实现的？

让我们聚焦在最核心的**步骤2**和**步骤5**，看看大模型内部是怎么“思考”的。

**1. 工具的“说明书”：如何让模型知道有工具可用？**

在调用发生之前，我们必须把所有可用的工具，以一种模型能理解的方式“告诉”它。这通常是通过在发给模型的提示词（Prompt）中，加入详细的**工具描述（Function Calling 的 API 描述）**来实现的。

这个描述就像一份给模型的说明书，里面详细说明了每个工具：

-   **工具的名称**：例如 `get_weather`
-   **工具的描述**：例如 “获取指定城市的实时天气信息”
-   **工具的输入参数**：需要模型从用户问题中提取哪些信息。例如：
    -   参数名：`location` （城市）
    -   类型：`string` （字符串）
    -   描述：“城市名称，比如 北京、上海”

这份说明书通常以 JSON 格式呈现。模型通过训练和提示词的学习，理解了这份“说明书”的含义。

**2. 模型的“决策时刻”：如何决定调用哪个工具？**

当用户提问“北京今天天气怎么样？”时，大模型的处理过程如下：

-   **理解意图**：模型分析出用户想查询“天气”，这是一个需要实时信息的请求，而它的内部知识库里没有今天的天气。
-   **匹配工具**：模型会在自己的“记忆”中搜索，看哪个工具最适合。它发现有一个 `get_weather` 工具，描述是“获取指定城市的实时天气信息”，完美匹配。
-   **提取参数**：模型从用户问题中提取出必要参数“北京”，并将其对应到 `get_weather` 工具要求的 `location` 参数上。
-   **生成指令**：此时，模型**不会直接输出“北京今天天气晴朗”**，因为它不知道。它会输出一个**特殊的、结构化的响应**，内容大致是：“我需要调用 `get_weather` 工具，参数是 `{location: 北京}`”。

这个“特殊的响应”就是整个流程的关键。它不是自然语言，而是一个**“调用工具的请求”**，通常也是 JSON 格式。

**3. 系统的“执行环节”：谁来跑腿？**

大模型本身不执行代码。它输出这个结构化请求后，外部的**调度系统（或代码）**会接手：

-   **解析请求**：系统读取模型的输出，知道它想调用 `get_weather`，参数是“北京”。
-   **调用真实 API**：系统拿着这个信息，去访问一个真实的天气预报网站的 API，获取到“北京，25°C，晴”这样的数据。
-   **返回结果**：系统将获取到的数据，作为“工具调用的结果”返回给大模型。

**4. 模型的“最终作答”：如何组织答案？**

现在，大模型有了两个信息：用户的问题和工具返回的真实数据。它会进行第二次生成：

-   **输入**：用户问题 + 工具返回的结果（“北京，25°C，晴”）。
-   **处理**：模型现在有了准确的答案，它会像一个语言大师一样，将数据组织成一句通顺、友好、符合语法的回答。
-   **输出**：“北京今天天气晴朗，气温25°C，祝您有愉快的一天！”

这样，一个完整的工具调用过程就结束了。

### 总结

| 关键过程 | 核心任务 | 实现方式 |
| :--- | :--- | :--- |
| **1. 工具定义** | 让模型知道有哪些工具可用 | 在提示词中以 JSON Schema 等形式描述工具的**名称、功能、参数** |
| **2. 意图识别** | 模型判断是否需要调用工具，以及调用哪个 | 利用模型的语言理解和推理能力，在内部进行“决策” |
| **3. 参数提取** | 从用户输入中提取出工具需要的参数 | 模型的自然语言理解能力 |
| **4. 结构化输出** | 模型输出一个“调用指令”，而非自然语言 | 输出一个预定义格式的 JSON 数据，包含**工具名和参数** |
| **5. 外部执行** | 系统调用真实的 API 获取结果 | 外部代码负责与真实世界交互 |
| **6. 整合回答** | 模型将工具返回的结果与对话历史结合，生成最终答案 | 模型的**文本生成**能力 |

所以，大模型的工具调用能力，并非模型本身学会了使用工具，而是通过精心的设计，让模型成为一个智能的 **“决策者”和“翻译官”**，通过**结构化的输出**，指挥外部的系统去完成它力所不能及的任务。这正是当前大模型从单纯的聊天机器人，迈向能够解决实际问题的**智能体**的关键一步。

这个问题问得非常深入，直击了工具调用在实际应用中的核心挑战和实现细节。我们来逐一拆解。

# Q: 2、3、4如何保证的准确性？还是无法保证，通过大量的训练，提高了这种准确性？另外，4到5的具体过程是怎么样的？

### 一、步骤 2、3、4 的准确性：如何保证？

首先，一个诚实的答案是：**无法100%保证**。大模型的本质是概率性的，它的每一个输出都是基于海量数据计算出的“最可能的下一个词”。因此，在工具调用的每个环节都存在出错的可能。

但是，我们可以通过多种方法，**极大地提高**这种准确性，让它达到可用的水平。这些方法可以归结为**训练阶段**和**推理阶段**两个层面的努力。

#### 1. 训练阶段：让模型学会“使用工具”

现在的模型（如GPT-4， Claude-3等）在预训练之后，通常会经过一个专门的**微调**阶段，来学习工具调用。

-   **构造海量训练数据**：研究人员会创建大量的对话样本。在这些样本里，包含用户的问题、对应的“工具调用指令”（步骤4的结构化输出），以及后续基于工具结果生成的回答。
-   **让模型模仿学习**：通过在这些数据上进行微调，模型就学会了“模式匹配”。它明白了，当用户询问天气时，**大概率**应该输出一个 `get_weather` 的结构化请求，而不是直接回答。这个过程，就是让模型的权重参数记住了工具调用的“套路”。

#### 2. 推理阶段：通过“提示词”和“约束”来引导

这是决定最终准确性的临门一脚。在用户提问时，我们会在发送给模型的上下文中，加入非常关键的“引导信息”。

-   **精确的工具描述**：这就是我之前提到的“说明书”。它必须极其清晰、无歧义。例如，一个模糊的描述`“获取天气信息”`和一个精确的描述`“根据提供的城市名称，从天气API获取实时天气数据。城市名称必须是中文，如’北京’。”`，后者让模型准确理解工具功能的概率会高得多。这个描述的质量直接决定了步骤2和3的准确性。
-   **Few-shot示例**：在提示词中，除了工具描述，还可以加入几个“一问一答+调用示例”。这就像给模型提供几个“例题”，让它照猫画虎。例如：
    ```
    用户：上海热吗？
    助手：我需要调用 get_weather，参数是 {location: 上海}
    ```
    有了这样的示例，模型更容易理解它在什么时候该做什么事。

-   **约束解码**：在模型生成文本时，技术实现上可以强制它按照特定的格式（比如JSON）来输出。例如，一旦模型开始生成“工具调用”的部分，解码器可以限制它只能生成符合JSON语法的字符，从而保证步骤4的结构化输出是格式正确的。

**总结一下步骤2、3、4的准确性：**

它不是通过单一方法“保证”的，而是通过**“专项训练（让模型学会模式） + 清晰提示（让模型理解任务） + 格式约束（让模型正确输出）”** 的组合拳，将出错概率降到最低。

**可能失败的情况**：
-   **步骤2（意图识别失败）**：模型错误地认为一个不需要工具的问题需要调用工具，或者相反。比如，用户问“你好”，模型却去调用了天气工具。
-   **步骤3（参数提取错误）**：用户问“北京和上海哪里更冷？”，模型可能只提取了“北京”，而忽略了“上海”，只调用了一次工具。
-   **步骤4（结构化输出错误）**：模型输出了一个格式错误的JSON，比如缺少了引号或括号，导致外部系统无法解析。

### 二、步骤 4 到 步骤 5 的具体过程

这个“握手”过程是实现工具调用的关键桥梁，我们来详细拆解它。

**前提**：整个过程发生在一个**大模型应用程序**中，这个程序由两部分组成：
1.  **大模型**：负责思考和决策。
2.  **外部调度系统**：一段代码，负责与大模型通信，并执行实际操作。

#### 详细流程：

1.  **模型生成“特殊响应”（步骤4的输出）**
    -   模型根据用户的请求，决定调用 `get_weather` 工具。它不会生成“我想调用天气工具”这样的自然语言，而是生成一个**结构化的、机器易读的指令**。
    -   这个指令通常是JSON格式，它会包含一个特殊的字段（不同API命名不同，如 `function_call` 或 `tool_calls`），里面指明了工具名称和参数。
    -   **实际传输的数据可能是这样的：**
        ```json
        {
          "role": "assistant",
          "content": null,  // 通常内容为空，或者是一个说明
          "tool_calls": [
            {
              "id": "call_123abc", // 一个唯一的调用ID
              "type": "function",
              "function": {
                "name": "get_weather",
                "arguments": "{\"location\": \"北京\"}" // 注意，参数本身也是一个JSON字符串
              }
            }
          ]
        }
        ```

2.  **外部调度系统“解析”响应**
    -   调度系统（就是你写的Python/Node.js代码）接收到大模型API返回的整个数据包。
    -   它会检查这个数据包里是否包含 `tool_calls` 字段。
    -   如果包含，系统就知道：模型想要调用工具。然后它会解析出：
        -   `name`: `get_weather`
        -   `arguments`: `{"location": "北京"}`
        -   `id`: `call_123abc` (这个ID在后面会用到)

3.  **外部调度系统“执行”工具**
    -   系统现在有了明确的指令。它会根据 `get_weather` 这个名字，去执行一段预先写好的**真实代码**。
    -   **这段代码可能是这样的：**
        ```python
        # 伪代码
        if tool_name == "get_weather":
            location = extracted_args["location"]
            # 这里是真正的API调用！
            api_url = f"https://api.weather.com/current?city={location}"
            response = requests.get(api_url) 
            weather_data = response.json() # 拿到真实数据
            result = f"{location}的天气是{weather_data['condition']}，温度{weather_data['temp']}度。"
            # 将结果返回给大模型
        ```
    -   关键点：**大模型不执行任何代码，它只是发出指令。真正去调用API、连接数据库、发送邮件的，是这段外部代码。**

4.  **外部调度系统“返回”结果给模型**
    -   工具执行完毕后，调度系统需要把结果“喂”回给大模型，让它进行下一步处理。
    -   它会构造一条新的消息，这条消息的角色是 `tool`（工具），并且会带上之前那个 `tool_call_id`，以便模型能将结果与之前的调用请求对应起来。
    -   **发送给模型的下一轮消息可能是这样的：**
        ```json
        {
          "role": "tool",      // 角色是工具
          "tool_call_id": "call_123abc", // 对应之前的调用ID
          "content": "北京的天气是晴朗，温度25度。" // 工具返回的真实结果
        }
        ```
    -   同时，整个对话历史（用户的原始问题、模型的调用请求）也会一并再次发送给模型。

5.  **模型生成“最终回答”（步骤5）**
    -   大模型现在收到了新的输入：**完整的对话历史 + 工具返回的结果**。
    -   它看到自己之前要求调用 `call_123abc` 工具，而现在正好有一个 `tool` 角色的消息带着相同ID的结果回来了。它明白，这就是它要的信息。
    -   于是，它发挥自己的语言能力，将工具返回的干巴巴的数据（“北京的天气是晴朗，温度25度。”），结合用户的问题，组织成一个自然、友好的回答。
    -   **最终输出给用户：**
        “北京今天天气晴朗，气温25度，是个出门的好天气哦！”

**总结步骤4到5的流程：**

**模型（提出请求）** → **系统（解析并执行真实API）** → **系统（将结果封装成“工具消息”）** → **模型（整合信息，生成最终回答）**

这个过程就是一个清晰的 **“请求-执行-反馈-生成”** 的循环。大模型始终在它最擅长的领域工作——**理解和生成语言**，而将需要与真实世界交互的**确定性操作**，交给了外部的代码去完成。这种分工协作，正是工具调用能力强大而又可靠的基石。


## MCP、tool学习、skill的区别和联系是什么？是否可以理解为skill是tool后训练发展到一定阶段的产物？

你提的这个问题非常棒，触及了当前AI智能体（AI Agent）架构设计的核心。这三个概念确实是构建复杂AI应用时经常遇到的，但它们处于完全不同的抽象层次，扮演着不同的角色。你的猜测很有趣，但实际情况比“进化”要复杂一些，它们更像是一种**分工与协作**的关系。

为了清晰地解释，我们先分别给它们“定个位”，再来看它们如何协同工作。

### 🔍 三个概念的精确定位

1.  **MCP（模型上下文协议，Model Context Protocol）**：你可以把它理解为**工具界的“USB-C接口”或“万能插座”**。它是一个标准化的、开放的协议，旨在解决AI模型与各种外部数据源和工具连接时的“碎片化”问题。在MCP出现之前，每对接一个新的工具（比如天气API、数据库、搜索引擎），开发者都需要编写一套特定的适配代码。而有了MCP，只要工具支持这个协议，就可以通过统一的方式接入，大大简化了开发流程。**MCP的核心价值在于“连接”和“标准化”，它服务的是开发者，而非模型本身**。

2.  **Skill（技能）**：Skill可以看作是一份写给AI智能体看的 **“操作说明书”或“菜谱”**。它通常是用自然语言（写在Markdown文件里）描述的、指导AI如何完成一项特定任务的一系列指令。例如，一个名为“网页抓取”的Skill，其内容可能包括：“当用户要求抓取某个网页时，请使用 `scpr --url <网页地址>` 这个命令行工具，然后将返回的Markdown内容进行总结。” **Skill的核心在于“行为引导”和“流程编排”，它告诉AI“怎么做”**，但具体执行的效果，依赖于AI对自然语言指令的理解和推理能力，因此可能存在不确定性。

3.  **Tool Learning（工具学习）**：这不是一个具体的功能模块，而是指**大模型本身具备的一种核心能力**——也就是我们在前两轮对话中深入讨论的“工具调用”能力。它是指模型能够理解你提供的工具列表（工具的名称、描述、参数），并根据用户的提问，决定是否需要调用工具、调用哪个工具以及生成正确的参数（即输出结构化的调用指令）。**Tool Learning是模型内部的“智能决策”过程**，是连接用户意图和外部工具（无论这个工具是通过什么方式提供的）的桥梁。

### 🤝 它们的关系：不是谁取代谁，而是“三层协同”

基于以上定义，我们可以清晰地看到它们并非前后演进的关系，而是在智能体应用中扮演着不同层次的角色，协同工作。

| 概念 | 抽象层次 | 核心角色 | 类比  | 谁来使用 |
| :--- | :--- | :--- | :--- | :--- |
| **MCP** | **基础设施层** | **标准化“连接”** | 统一规格的**食材/厨具**（如煤气灶、自来水） | 开发者 |
| **Tool Learning** | **大脑决策层** | **智能化“决策”** | 厨师**决定**做什么菜、用什么厨具 | 大模型 |
| **Skill** | **行为编排层** | **流程化“引导”** | 贴在墙上的**菜谱**（指导厨师如何做菜） | 大模型 |

用一个完整的例子来看看它们是如何协作的：

假设你开发了一个智能体，想让它拥有“分析上个月销售数据并生成报表”的能力。

1.  **Skill（菜谱）**：你会先写一个Skill，里面用自然语言描述了步骤：“1. 调用`query_sales_data`工具，获取上个月的销售数据。2. 对返回的数据进行总结，计算总销售额和增长率。3. 调用`generate_chart`工具，将数据生成柱状图。4. 将总结文字和图表整合成最终答案。”
2.  **MCP（基础设施）**：`query_sales_data`和`generate_chart`这两个工具，是通过MCP协议接入系统的。这意味着它们以标准化的方式呈现在工具列表中，开发者不需要为它们编写特殊的调用代码。
3.  **Tool Learning（决策）**：当用户提问时，大模型发挥其Tool Learning能力，它会“阅读”并“理解”你提供的Skill（菜谱），然后根据Skill的指导，一步步地通过MCP去调用底层工具，获取数据、生成图表，最后完成任务。

所以，你的猜测“skill是tool后训练发展到一定阶段的产物”非常具有启发性，它看到了从“能调用单个工具”到“能完成复杂任务”的演进趋势。但从技术实现上看，**Skill并非Tool Learning的进化产物，而是建立在Tool Learning基础之上的高级应用模式**。Tool Learning赋予了模型使用工具的“本能”，而Skill则进一步为这种“本能”提供了结构化的“行为框架”，让模型能完成更复杂的、多步骤的工作流。MCP则作为背后标准化的“基础设施”，让工具的接入和管理变得更高效。

希望这个解释能帮你理清这三个关键概念。既然聊到了AI智能体，你想不想了解一下，当模型根据Skill执行一个多步任务时，又是如何保证中间步骤不出错的？或者我们聊聊目前主流的几种智能体架构（比如ReAct）？


# Q: 对，这也是我想了解的。模型具备了拆解问题的能力，然后可能会安排多个步骤调用不同的tool。这类系统是如何完成自动多步执行的？

当模型具备了调用工具的能力后，自然就引出了一个新的问题：如何让模型**自主地、一步一步地**完成一个复杂任务？比如用户问“帮我查一下北京和上海的天气，然后对比一下，并写一封邮件告诉我的朋友”，这就需要模型先查北京天气，再查上海天气，然后对比，最后调用邮件工具。整个过程涉及多个步骤，且步骤之间可能有依赖（比如对比需要两个结果）。

这种自动多步执行的背后，通常是一个被称为 **“智能体循环”** 的机制，其中最经典的范式就是 **ReAct（Reason + Act，推理+行动）**。下面我们详细拆解它是如何工作的。

---

### 一、核心思想：让模型进入“思考-行动-观察”循环

多步执行的关键在于，我们不再期望模型一次性完成所有事情，而是让它进入一个循环：

1.  **思考**：模型根据当前的问题和已有的信息，决定下一步该做什么。
2.  **行动**：模型调用一个工具（或者输出一个最终答案）。
3.  **观察**：系统执行工具，将结果返回给模型。
4.  **重复**：模型拿到新信息，再次“思考”，直到它认为任务完成，输出最终答案。

这个过程就像一个人在处理复杂任务时，先想想需要做什么，然后做一步，看看结果，再想下一步怎么做。

---

### 二、具体实现过程（以一次多步天气查询并对比为例）

假设用户提问：“北京和上海今天天气怎么样？哪个更暖和？然后帮我把结果发邮件给张三。”

整个交互过程在后台会展开成多个来回：

#### 第1轮：用户提问 + 初始上下文
-   **用户**：北京和上海今天天气怎么样？哪个更暖和？然后帮我把结果发邮件给张三。
-   **系统发给模型的内容**：包含用户问题，以及所有可用的工具描述（天气工具、邮件工具）。模型开始**思考**。

#### 第2轮：模型第一次响应（思考+行动）
模型在内部会生成类似这样的内容（但最终输出给系统的是一个结构化的调用指令）：
> **思考**：用户需要查询两个城市的天气，然后对比，最后发邮件。我应该先查询北京的天气。
> **行动**：调用 `get_weather` 工具，参数 `location=北京`。

系统接收到这个工具调用请求，执行天气API，得到结果：“北京，晴，25°C”。系统将这个结果作为**观察**，连同之前的对话历史，一起发送给模型，进行下一轮。

#### 第3轮：模型第二次响应（思考+行动）
模型看到新信息：
-   **用户**：...（原始问题）
-   **助手（上一轮）**：调用了 `get_weather`（工具请求）
-   **工具（观察）**：北京，晴，25°C

模型开始新的**思考**：
> **思考**：我已经拿到了北京的天气，现在需要上海的天气。然后才能对比。
> **行动**：调用 `get_weather` 工具，参数 `location=上海`。

系统再次执行工具，得到“上海，多云，22°C”，并将此观察发回。

#### 第4轮：模型第三次响应（思考+行动）
现在模型拥有了两个数据：
-   北京：晴，25°C
-   上海：多云，22°C

模型思考：
> **思考**：两个天气都有了。北京25°C，上海22°C，所以北京更暖和。现在需要把结果整理成邮件发给张三。
> **行动**：调用 `send_email` 工具，参数 `recipient=张三`，`content=北京今天晴天25°C，上海多云22°C，北京更暖和。`

系统执行邮件发送，成功后返回“邮件已发送”的观察。

#### 第5轮：模型最终回答
模型看到邮件发送成功的反馈，认为任务已经完成，于是生成最终的自然语言回答给用户：
> 北京的天气是晴天25°C，上海是多云22°C，北京更暖和。我已经把对比结果通过邮件发送给了张三。

---

### 三、实现多步执行的关键技术细节

#### 1. 如何让模型知道什么时候该停？
-   通常有两种方式：
    -   **模型自行判断**：在提示词中告诉模型，如果你认为任务已经完成，就直接输出最终答案，不要再调用工具。模型在生成时，如果判断没有需要继续的行动，就会生成一个**最终回答**（通常是自然语言，不带工具调用字段）。
    -   **系统强制终止**：设定最大迭代次数（如最多10轮），防止无限循环。

#### 2. 如何保持上下文？
-   每一轮交互，系统都会把**完整的对话历史**（包括用户问题、之前的助手思考和行动、工具返回的观察）都发送给模型。这样模型就能“记住”之前已经做了哪些步骤，获得了哪些中间结果。

#### 3. 如何让模型的“思考”对用户可见？
-   很多智能体应用（如AutoGPT、Claude的Computer Use）会把模型的“思考”过程也展示给用户，比如显示“正在查询北京天气...”。这既是透明性的体现，也让用户能理解模型为什么这么做。通常，模型会在输出中同时包含“思考”文本和“行动”指令。

---

### 四、ReAct 模式 vs. 纯粹的“行动”模式

你可能已经注意到，上面的例子中模型输出了“思考”步骤。这其实是一种被称为 **ReAct** 的模式，它明确地让模型先生成一段推理，再生成行动。这样做有几个好处：

-   **提高可解释性**：你可以看到模型每一步的“心路历程”。
-   **减少错误**：强制模型先思考再行动，能减少盲目调用工具的概率。
-   **支持复杂推理**：有些任务需要多步推理（比如数学题），ReAct能让模型把中间推理过程写下来，就像人类打草稿一样。

在技术上，ReAct是通过在提示词中给出示例（few-shot）或通过指令微调实现的。例如，提示词里会写明：
> 你是一个智能助手，可以一步一步思考并调用工具。在每一步，你需要输出：
> Thought: （你当前的思考）
> Action: （你要调用的工具名称和参数）

然后系统解析 `Action:` 后面的内容去执行工具，工具的结果以 `Observation:` 的形式返回，模型再继续生成下一轮的 `Thought:`。

---

### 五、Skill 与 动态多步执行的关系

你之前问到的 Skill（技能），在这里扮演的角色是什么呢？

-   **Skill 是预定义的“菜谱”**：如果你把“查询两地天气并对比发邮件”这个流程写成了一个 Skill 文件（用自然语言描述步骤），那么模型在执行时，可以**阅读这个 Skill 作为指导**，然后按照 Skill 的步骤去调用工具。这相当于给了模型一个“计划”。
-   **动态多步执行是模型的“临场发挥”**：即使没有预定义的 Skill，模型也可以凭借其自身的规划能力，动态地将用户的问题分解成多个步骤并执行。这种能力来自于模型在海量数据中学习到的“如何一步步解决问题”的通用知识。

所以，Skill 是一种**强引导**，而动态多步执行是模型**自主规划**的体现。在实际系统中，两者可以结合：先用 Skill 给模型一个框架，模型在执行过程中，如果遇到 Skill 中没有覆盖的情况，也可能需要临时决策。

---

### 六、面临的挑战

自动多步执行虽然强大，但也有其难点：

1.  **错误累积**：如果某一步调用工具出错（比如天气API挂了），模型需要能识别错误并重新规划（比如尝试其他天气源，或者告诉用户暂时无法获取）。
2.  **长期依赖**：任务步骤很多时，模型可能会“忘记”最开始的目标，或者混淆中间结果。这需要模型有强大的长上下文理解和推理能力。
3.  **效率问题**：每调用一次工具就需要一轮模型推理，多步任务会导致响应时间变长。
4.  **安全与权限**：多步执行可能让模型无意中执行了危险操作（比如删除文件），所以必须对工具调用做严格的权限控制。

---

### 总结

-   **自动多步执行**的核心机制是 **“思考-行动-观察”循环**（ReAct）。
-   系统负责在每次模型输出工具调用时，执行工具，并将结果作为新的一轮上下文返回给模型，如此反复，直到模型输出最终答案。
-   这种能力让 AI 智能体能够自主完成复杂任务，是实现真正通用智能体的关键一步。
-   它与 **Skill**（预定义流程）互为补充，Skill 提供指导，多步执行提供灵活性。

# Q: 所以ReACT具体是怎么实现的，如何把一个只会生成的模型变为一个具备反馈循环的智能体的？
ReAct（Reason + Act，推理+行动）模式是目前将普通大模型转变为能自主执行多步任务的智能体最主流的方法。它的实现并不需要对模型本身进行结构改造，而是通过**巧妙的提示词设计**和**外部的程序循环**，让模型的行为模式从“单次生成”变为“迭代思考-行动-观察”。

下面我们一步步拆解它的具体实现。

---

## 一、核心思想：把“循环”交给外部代码，把“思考”留给模型

大模型本质上是一个**一次性的文本生成器**：给它一段输入，它生成一段输出，然后结束。要让模型进入循环，我们需要在**模型外部**编写一个**驱动循环**：

1.  **向模型发送包含当前状态（思考、已有观察）的提示**。
2.  **模型生成一段文本**，其中可能包含思考过程和行动指令。
3.  **外部代码解析模型输出**，如果发现它想调用工具，就执行工具，并将结果（观察）作为新的一轮输入的一部分，再次发送给模型。
4.  重复，直到模型输出最终答案。

这个外部循环是“反馈循环”的**骨架**，而模型内部的“思考”是**血肉**。

---

## 二、具体实现步骤（以代码视角）

### 1. 设计 ReAct 提示词模板

这是最关键的一步。我们需要告诉模型：“你是一个智能体，你要按照 Thought → Action → Observation 的格式一步一步思考并行动，最终输出 Final Answer。”

系统提示可以这样写（以文本形式，通常放在对话的 system 角色中）：

```text
你是一个可以调用工具来完成任务的智能助手。请按照以下格式一步一步执行：

Thought: 你现在需要思考：根据用户的问题和已有的信息，下一步应该做什么。
Action: 你需要调用的工具名称和参数，格式为：工具名(参数)，例如：get_weather(北京)
Observation: 工具返回的结果（这一步将由系统提供，你不需要生成）
...（可重复多次 Thought/Action/Observation）
Thought: 任务完成，我可以给出最终答案了。
Final Answer: 对用户的最终回答。
```

为了帮助模型理解，我们通常会提供一两个**few-shot 示例**，放在提示词里或历史消息中：

```text
用户：今天北京天气怎么样？
助手：
Thought: 用户想知道北京的天气，这需要实时信息，我应该调用天气工具。
Action: get_weather(北京)
Observation: 北京，晴，25°C
Thought: 我已经拿到了天气信息，可以回答用户了。
Final Answer: 北京今天天气晴朗，气温25°C。
```

### 2. 构建驱动循环（伪代码）

```python
def run_agent(user_query, tools, max_steps=10):
    # 初始化对话历史，包含系统提示、few-shot示例和用户问题
    messages = [
        {"role": "system", "content": REACT_SYSTEM_PROMPT},
        {"role": "user", "content": user_query}
    ]
    
    for step in range(max_steps):
        # 1. 调用大模型，生成回复
        response = call_llm(messages)
        
        # 2. 将模型的回复添加到历史中
        messages.append({"role": "assistant", "content": response})
        
        # 3. 解析模型的回复，判断是否包含行动指令
        if "Action:" in response:
            # 提取行动指令，例如 "Action: get_weather(北京)"
            action_str = extract_action(response)
            tool_name, args = parse_action(action_str)
            
            # 4. 执行工具调用（真实API调用）
            observation = execute_tool(tool_name, args)
            
            # 5. 将观察结果作为一条新消息加入历史（通常用 tool 角色）
            messages.append({"role": "tool", "content": observation})
            # 注意：有些实现直接拼接成 "Observation: ..." 的文本，但现代API推荐用 tool 角色
            
            # 循环继续，让模型基于观察继续思考
        elif "Final Answer:" in response:
            # 提取最终答案并返回
            final_answer = extract_final(response)
            return final_answer
        else:
            # 异常情况：模型没有按格式输出，可能需要重试或报错
            # 可以尝试让模型重新生成，或者返回当前内容
            return response
    
    # 超过最大步数，返回超时信息
    return "任务执行超时"
```

### 3. 关键细节

-   **解析模型输出**：模型生成的文本是自然语言，我们需要通过正则表达式或简单的字符串查找提取 `Action:` 后面的内容。例如 `Action: get_weather(北京)`，解析出工具名 `get_weather` 和参数 `{"location": "北京"}`。
-   **工具执行**：这一步完全是外部代码的责任。`execute_tool` 会调用真实的 API（如天气接口）并返回结果字符串。
-   **将观察结果返回给模型**：可以用两种方式：
    -   **文本拼接**：直接将 `Observation: {工具返回结果}` 作为一段文本附加到对话历史中，然后再次调用模型。
    -   **使用 tool 角色**：现代大模型 API（如 OpenAI 的 `tool` 角色）支持将工具结果以专门的消息类型传入，这样模型能更准确理解这是工具的输出。例如：
        ```python
        messages.append({"role": "tool", "tool_call_id": "xxx", "content": observation})
        ```
        这需要配合模型的 function calling 接口使用，但核心思想相同。
-   **停止条件**：当模型输出了 `Final Answer:` 或达到最大步数时，循环结束。

### 4. 微调（可选）：让模型更适应 ReAct

虽然通过提示词就能让许多现代模型（如 GPT-4）理解 ReAct，但如果你希望模型**更可靠、更高效**，可以对模型进行**微调**。微调的数据集就是大量包含 ReAct 格式的对话样本，让模型学习到这种格式的内在规律。微调后，模型在生成时会更倾向于输出符合格式的内容，减少解析失败率。

---

## 三、一个更贴近实际的例子（结合 Function Calling）

很多 API 已经内置了工具调用能力，比如 OpenAI 的 **Function Calling**。在这种情况下，ReAct 循环可以更简洁：

1.  **系统提示**中仍可包含 ReAct 格式的描述，但工具定义通过 API 的 `tools` 参数传入。
2.  模型输出不再是自然语言文本，而是一个结构化的对象，其中可能包含 `tool_calls` 字段。
3.  外部代码判断如果 `tool_calls` 存在，则执行相应工具，并将结果通过 `tool` 角色返回。
4.  模型基于工具结果自动进行下一轮推理，直到它生成一个不带 `tool_calls` 的普通文本回答。

这种方式的优点是不用手动解析 Action，模型直接输出结构化的调用请求，更稳定。

---

## 四、从“只会生成”到“具备反馈循环”的本质转变

通过以上设计，我们实际上是在模型外面包了一层**控制循环**，而模型本身并没有变成循环体，它依然是一个“单次生成器”。但通过反复调用它，并让它看到自己之前的输出和外部反馈，就形成了**反馈循环**的假象。这种模式的核心要素是：

-   **状态持久化**：每次调用都把整个历史（思考、行动、观察）传给模型，让模型拥有短期记忆。
-   **外部工具执行**：模型只负责决策和语言生成，实际操作由外部代码完成。
-   **格式约束**：通过提示词或微调，让模型的输出遵循某种格式，便于解析。

---

## 五、ReAct 与其他智能体模式的联系

你之前提到的 **Skill**（技能）可以视为一种**预定义的、高层次的 ReAct 流程**，而 ReAct 本身是底层的通用循环机制。Skill 可以作为提示词的一部分注入到 ReAct 循环中，指导模型按照既定的步骤走，同时保留 ReAct 的灵活性。

---

## 总结

ReAct 的具体实现可以分为三步：

1.  **设计提示词**：告诉模型按照 Thought → Action → Observation → Final Answer 的格式工作。
2.  **编写循环代码**：反复调用模型，解析其输出，执行工具，返回观察，直到得到最终答案。
3.  **管理对话历史**：确保每次调用都包含完整的上下文，让模型“记住”已经发生的事情。

这样，一个原本只能“一次性回答”的模型，就变成了能够“边思考边行动”的智能体。这种模式是当前所有 AI 智能体框架（如 LangChain, AutoGen, CrewAI）的基石。

# Q: 现有的主流商业模型都是这种React+function calling架构吗？
简单直接的回答是：**是的，这确实是目前（2026年）绝大多数主流商业模型和AI智能体应用的核心架构**。

可以把 **“ReAct + Function Calling”** 看作是构建智能体的“黄金组合”和“事实标准”。它们的分工非常明确：

*   **Function Calling（工具调用）**：提供的是 **“行动接口”**。它让模型能够理解工具、输出结构化的调用指令，是模型与外部世界交互的“手”和“口”。
*   **ReAct（推理与行动循环）**：提供的是 **“决策框架”**。它驱动模型进入“思考-行动-观察”的循环，让模型能够为了完成一个复杂目标，动态地、一步一步地规划和调用工具。

通过你之前了解的驱动循环，将这两者结合起来，就构成了目前最主流的智能体范式。这种组合之所以能被所有主流模型（如GPT系列、Claude系列、Gemini、通义千问、文心一言等）广泛采纳，是因为它足够灵活和强大，能应对大部分动态的、不确定的任务。

### 🔍 主流架构之外的探索：不止一种“智能”

不过，技术总是在演进。为了适应更复杂、要求更严格的企业场景，业界也在ReAct+Function Calling的基础上发展出了一些变体和探索。它们并非取代关系，而是在特定维度上的优化和补充。

我把它们整理成了一个表格，这样对比起来会更清晰：

| 架构形态 | 核心特点 | 与ReAct+Function Calling的关系 | 适用场景举例 | 代表案例/来源 |
| :--- | :--- | :--- | :--- | :--- |
| **标准形态：ReAct + Function Calling** | **动态决策**，边想边做，灵活性强。 | 这是 **“底座”和“原型”**，其他形态大多基于此演进。 | 开放域的问答、个人助手、需要灵活应变的任务。 | 几乎所有模型API的默认智能体模式。 |
| **结构化形态：Pre-Act (计划先行)** | **先计划后执行**，强调整体流程的**可控性和一致性**。 | 针对ReAct在**长流程、高合规**场景下“容易走偏”的痛点进行优化，先定好路线图再行动。 | 企业级复杂工作流（如保险理赔、贷款审批）、需要严格合规的业务。 | Uniphore公司提出的Pre-Act框架。 |
| **协议化形态：MCP (模型上下文协议)** | **标准化连接**，作为“万能插座”统一工具接入方式。 | 不与ReAct竞争，而是为Function Calling提供更高效的**基础设施**。它优化了“行动”这一步，让工具管理更方便。 | 需要接入大量、复杂、异构第三方服务的应用。 | Anthropic推动的开放协议，被社区广泛接受。 |

### 💡 总结

所以，你的理解是准确的。**ReAct + Function Calling** 确实是当前的主流，几乎所有你能叫上名字的商业模型都在这个框架下构建其智能体能力。

而 **Pre-Act** 和 **MCP** 的出现，恰恰说明了这个领域正在走向成熟和细分：

1.  **Pre-Act** 代表了在 **“流程控制”** 维度上的深化，让AI在处理确定性任务时更可靠。
2.  **MCP** 代表了在 **“工具连接”** 维度上的标准化，为AI能够调用海量工具铺平了道路。

如果说ReAct+Function Calling让AI学会了“走路和说话”，那么Pre-Act就是在教它“按图纸施工”，而MCP则是为它修建了通往四面八方的“标准化公路”。这三者共同构成了2026年AI智能体生态的基石。

你未来在构建自己的智能体应用时，完全可以从最标准的ReAct+Function Calling入手。当你发现需要处理非常复杂且步骤固定的企业流程时，可以借鉴Pre-Act的思想；当你需要接入大量第三方服务时，拥抱MCP生态会是最高效的选择。

# Q: ReAct模型工作过程中，附加的各种特殊字符应该不属于自然语言的范畴了吧，都是靠微调学出来的，那为什么我们和现在的大模型对话时，没有出现这些特殊字符？
你的问题触及了AI智能体在实际应用中的一个关键设计：**如何平衡模型的内部工作机制与用户交互体验**。简单来说，这些特殊字符确实是模型通过微调学会的“工作语言”，但在面向用户的对话中，它们被应用层巧妙地隐藏或转化了。

---

## 一、这些特殊字符是如何被模型学会的？

### 1. 它们属于“提示语言”，而非自然语言
`Thought:`、`Action:`、`Observation:` 这类标记，本质上是一种**结构化的提示指令**，目的是引导模型按照特定格式输出，便于外部程序解析。虽然它们由英文单词和标点组成，但在训练语境中，模型被教会了这些标记的“特殊含义”：

-   当模型看到 `Thought:` 时，它知道自己应该输出一段内部推理。
-   当模型看到 `Action:` 时，它知道自己需要生成一个工具调用指令。
-   当模型看到 `Observation:` 时，它知道这是工具返回的结果，需要据此继续推理。

### 2. 学习方式：指令微调 + 示例学习
-   **指令微调**：在模型的微调阶段，研究者会构造大量包含这些标记的对话样本（比如多轮ReAct格式的对话）。模型通过模仿这些样本，学会了在何时输出 `Thought:`、何时输出 `Action:`，以及如何根据 `Observation:` 更新自己的下一步输出。
-   **上下文学习**：在实际使用中，即使没有经过专门微调的模型，也可以通过提示词（系统消息+few-shot示例）学会这种格式。提示词中会明确说明格式要求，并提供示例，模型通过理解上下文来遵循。

### 3. 为什么这些字符不是自然语言？
因为它们的主要功能是**控制流**而非**语义表达**。就像HTML标签不是自然语言一样，它们是给程序（或模型自身）看的指令。但模型确实“理解”了这些标记的语义，因为它们出现在自然语言上下文中，模型学会了将“Thought:”后面的内容理解为推理，将“Action:”后面的内容理解为需要执行的命令。

---

## 二、为什么我们在日常对话中看不到这些字符？

这背后有两个层面的原因：**应用层过滤** 和 **模型行为控制**。

### 1. 应用层过滤与界面美化
当你使用像ChatGPT、Claude这样的聊天界面时，你看到的只是最终呈现。实际上，模型在后台可能输出了包含这些标记的内容，但前端应用做了处理：

-   **只显示最终答案**：如果模型在一轮对话中既生成了 `Thought` 又生成了 `Final Answer`，应用可以解析出 `Final Answer` 部分并显示给用户，而把中间的思考过程丢弃或仅在调试模式下显示。
-   **将思考过程转化为友好提示**：有些应用（如某些AI助手）会把模型的思考过程转化为用户可见的“正在思考...”或“正在查询...”等动态提示，而不是直接显示 `Thought:` 这种生硬的标记。

### 2. 模型在“最终回答”模式下不输出标记
在很多实际产品中，模型并不是一直在ReAct模式下运行。系统会根据任务需要动态切换“思考模式”和“对话模式”：

-   **对话模式**：当用户只是闲聊或问一个简单问题时，系统提示中不包含ReAct格式要求，模型直接以自然语言回答，自然不会输出 `Thought:` 之类的标记。
-   **智能体模式**：当用户触发需要调用工具的任务时，系统会在提示中加入ReAct格式说明（通常通过system消息），模型才会按照格式输出。但即使如此，在最终生成答案时，模型会输出 `Final Answer:` 后的内容，应用可以提取这部分呈现给用户，隐藏其他部分。

### 3. 后端API与前端分离
在实际API调用中，比如OpenAI的Chat Completion接口，如果你通过 `tools` 参数启用函数调用，模型返回的是一个结构化的JSON对象，其中可能包含 `tool_calls` 字段，而 `content` 字段可能是空或包含思考过程。开发者可以自由选择如何展示这些信息。普通用户通过网页界面看到的，是开发者决定展示的内容。

---

## 三、一个具体的例子：ReAct在后台 vs. 前台

假设用户问：“北京天气怎么样？”

**后台真实交互（简化）**：
```
系统提示（包含ReAct格式说明）：
你是一个智能助手，请按照以下格式回答：
Thought: ...
Action: ...
Observation: ...
Final Answer: ...

用户：北京天气怎么样？

模型第一轮输出：
Thought: 用户想查询北京的实时天气，我需要调用天气工具。
Action: get_weather(北京)

系统执行工具，得到“北京，晴，25°C”，作为Observation附加到对话。

模型第二轮输出：
Thought: 我已经拿到天气信息，可以回答用户了。
Final Answer: 北京今天天气晴朗，气温25°C。
```

**用户看到的前台**：
```
北京今天天气晴朗，气温25°C。
```

中间的 `Thought`、`Action`、`Observation` 都被应用过滤掉了，或者转化为一个简短的“正在查询...”提示。

---

## 四、总结

-   **特殊字符是模型通过微调和提示学习的工作语言**，它们不属于自然语言，但模型能够理解并使用它们来完成多步任务。
-   **日常对话中看不到它们**，是因为应用层（前端/API调用方）通常会过滤掉中间过程，只向用户展示最终的自然语言答案，或者在特定情况下将思考过程转化为更友好的用户界面元素。
-   这种设计既利用了模型的强大规划能力，又保持了用户交互的自然流畅，是智能体落地产品的关键工程实践。

如果你有机会查看API返回的原始数据，或者使用一些开发工具（如LangChain的调试模式），你就能看到这些隐藏在背后的特殊字符了。
